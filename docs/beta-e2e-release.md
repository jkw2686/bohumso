# 클로즈드 베타 E2E 적용·검증 — 2026-10-05

## 적용 범위

일반 정책 승인을 변경하지 않고 별도 버전 동의와 초대로 베타 참여를 허용한다. 기존 Google/이메일 로그인은 계속 제공한다. 고객은 보험소와 시간을 선택하고 관리자가 전문가를 배정한다. 직접 전문가 요청 경로도 기존 예약과 호환된다.

- 028: 해시 초대, 사용횟수 잠금, 동의 기록, 베타 전화 확인, 운영 현황.
- 029: 전문가 검토, 공개 지역 중심점, 베타 예약 표시, 요청/변경/배정 슬롯 잠금.
- `ADMIN_TESTER`는 관리자 권한을 받지 않는다.
- `is_beta=false`인 기존 예약은 그대로 보존한다.
- 익명/일반 회원은 베타 전문가를 볼 수 없다. 베타 전문가의 신분·자격을 공개 인증으로 표시하지 않는다.

## 운영 반영 전 조건

1. 기존 027까지의 실제 운영 상태에서 **028과 029만** 순서대로 적용한다. 누락된 011을 포함한 전체 migration 실행은 금지한다. 두 파일과 이력 기록을 한 트랜잭션으로 적용하는 검토본은 outputs에 준비한다.
2. 서버 전용 난수 64자리 이상을 private.beta_gateway와 Netlify `BETA_GATEWAY_SECRET`에 동일하게 설정한다. 비밀값을 소스, 브라우저 자산, 로그, 보고서, 채팅에 남기지 않는다. Supabase 사용자 JWT 검증과 함께 사용되는 서버 요청 확인용이며 관리자 서비스 역할 키를 대신 발급하지 않는다.
3. 공개 가입·결제·SMS·서류·실시간/백그라운드 위치 플래그를 유지한다. 베타 초대와 동의가 없어도 기존 계정 로그인은 가능하다.
4. SQL 성공 후 RLS와 execute 권한을 다시 조회한다. 베타 전용 private 테이블은 직접 anon/authenticated 조회 불가여야 한다.
5. 미리보기에서 아래 실계정 검증 후 한 번만 Production 배포한다. 현재 로컬 검증을 운영 성공으로 대체하지 않는다.

## 실제 참여자가 필요한 검증

사용자가 소유하고 베타 동의한 고객 2계정과 전문가 1계정을 사용한다. 다른 기존 사용자를 테스트용으로 전환하거나 auth.users에 가짜 사용자를 삽입하지 않는다. 비밀번호·OTP·메일 인증은 본인이 수행한다. 관리자 전화 확인은 실제 확인한 번호에만 적용한다.

1. 관리자: 고객/전문가 초대(허용 이메일, 1회, 짧은 만료) 생성. 원본 코드는 생성 시 한 번 복사하고 보고서에는 기록하지 않는다.
2. 고객: 초대→Google 또는 이메일 확인→베타 동의→원래 상황/예약 페이지 복귀. 세션 유지·로그아웃·기존 이메일 로그인·재발송·비밀번호 재설정 확인.
3. 전문가: 동의→관리자 전화 확인→이름/소속/분야/시간→주활동지역과 추가 최대2곳→검토 요청. 관리자 승인 전 지도·고객정보가 보이지 않아야 한다.
4. 관리자: 신청 검토 후 베타 지도 승인. 고객으로 지역 중심점만 노출되는지 확인. 정확한 GPS·집주소·문서 수집 없음.
5. 고객 요청→관리자 배정(보험소 예약)→전문가 수락→고객 확정상태→예약시간 경과→전문가 완료요청→고객 완료확인. **5건을 실제 시간에 따라 완료한다. 운영 예약시간을 SQL로 과거로 바꾸지 않는다.**
6. 서로 다른 두 고객 세션에서 같은 전문가/시간 요청을 동시에 전송. 성공1·실패1 및 실제 DB 행 수 확인. 프런트 버튼 차단만으로 성공 처리하지 않는다. 테스트 중 생성한 예약은 정상 취소 기능으로 정리한다.
7. 고객B가 고객A 예약 ID로 조회/취소/시간변경을 시도하면 권한 오류. 미승인 전문가와 일반 회원의 관리자/초대 API 차단. 승인 중지 시 지도·전문가 작업공간 접근 차단.
8. Android Chrome과 Desktop에서 위치 허용→실좌표·내 위치·거리, 거부→재시도/지역 선택, 상황 이동 후 위치 출처 유지. 접속지역 추정은 실GPS 성공으로 기록하지 않는다.

## 이번 검증의 한계

- 로컬 DB 테스트는 PGlite, 인증 UI는 모의 Google/email PKCE이다. 실제 Supabase 다중 연결 경쟁 테스트가 아니다.
- 운영 API 차단과 RLS 활성 수는 실제 서버 읽기 점검했다. 실제 사용자별 JWT 권한 검증은 참여 계정 확보 후 수행한다.
- 운영 webhook은 비활성 상태에서 먼저 차단된다. 활성 결제 provider 서명/결제조회 검증 성공을 주장하지 않는다.
- 계정·예약 자료의 일반 보유기간과 자동삭제, 외부 발송 공급자 계약, 일반 공개 정책 확정은 별도 과제이다.
