## 계산·제한 설계

1. **90일 기준**: 운영자의 사실 확인 시점에서 90일을 역산하되, 사건의 발생 시각(합의한 약속 시간)을 기준으로 포함한다. 시행일 이전 발생 건은 제외한다. 발생·접수·판정 시각과 정책 버전을 구분한다.
2. **확정만 계산**: 한 예약은 하나의 사건. `consumer_absent` 또는 `expert_absent`의 최신 판정만 해당 역할의 횟수에 포함한다. 신고 접수와 사실 확정은 별도 기록이다.
3. **동시 확정**: 계정·역할별 트랜잭션 잠금으로 계산을 직렬화한다. 동일 계정에 대해 서로 다른 사건을 동시에 처리해도 중복 제한을 만들지 않는 구조다. 실제 다중 PostgreSQL 연결 경합은 미검증이다.
4. **소비자**: 1회 경고, 2회 새 신청 3일, 3회 7일. **전문가**: 1회 경고, 2회 새 접수·수락 7일, 3회 30일 + 운영자 재개 확인.
5. **제한 중 추가 사건**: 기존 종료 시각을 유지하고 추가 검토 표시를 남긴다. 자동 합산·연장하지 않는다. 예를 들어 2회 제한 중 3회째가 확인되면 자동으로 기간을 늘리지 않는다. 운영자의 추가 집행 방식은 별도 결정 대상이다.
6. **4회 이상**: 개별 검토. 자동 영구정지 없음. 이미 유효한 제한은 원래 종료 시각대로 유지한다.
7. **번복**: 최신 판정으로 다시 계산한다. 낮은 단계가 되면 기존 시작 시각에 낮은 기간을 적용해 종료를 단축하거나 해제한다. 번복으로 기간이 늘어나지 않는다.
8. **종료**: 소비자와 전문가 2회 제한은 기간 종료 후 해제. 전문가 3회는 운영자 확인까지 새 접수·수락 차단. ON/OFF 저장값은 변경하지 않는다.
9. **유료 전문가**: 활성·확인 중·환불 처리 중 구독은 보수적으로 유료로 취급한다. 관련 요금 기준과 사전 안내 승인 전 신규 예약 제한은 보류하며, 사건 검토와 경고 기록은 가능하다. 결제·환불·이용기간 수정 없음.

제한은 새 신청/접수/수락과 새 후속 약속에만 적용한다. 기존 약속의 조회·연락·변경·취소·이행·운영자 문의는 가능하다. 공개 사유나 불량 배지를 추가하지 않는다. 공개 조회에는 현재 새 요청 가능 여부만 반영하며 실제 ON/OFF 값과 구분한다.

## DB 영향 및 보안

초안: `supabase/055_appointment_care.sql`. 단일 `begin/commit`, 반복 실행, 기존 함수 백업, 직접 접근 revoke, 인증 사용자용 RPC, 비공개 표 RLS 사용.

새 비공개 표:

- `appointment_care_backup`: 기존 함수 원본
- `appointment_policy`: 버전·시행일·집행 스위치
- `appointment_care`: 기존 예약을 참조하는 약속 조건·확인 상태
- `appointment_changes`, `appointment_events`: 변경 제안·행동 이력
- `appointment_cases`, `appointment_statements`, `appointment_decisions`: 신고·양쪽 설명·판정 이력
- `appointment_measures`: 역할별 조치, 시작·종료, 재개 확인
- `appointment_receipts`: 재시도 식별자와 요청 해시. 주소·전화·설명 원문을 복제하지 않음
- `appointment_reminders`: 예정 시각·수신자·처리 상태
- `notifications`: 기존 표가 없을 때만 동일 구조로 생성

기존 회원·예약 컬럼 삭제/타입 변경/회원 삭제/예약 일괄 삭제/Storage 정책 변경 없음. 기존 함수는 백업 후 래핑한다. 원래 함수로 직접 우회하는 실행 권한은 막는다. 소스 예약·알림에 대한 기존 동작과 권한은 그대로 호출한다.

**정리 작업 주의**: SQL에 `DELETE`가 전혀 없다는 의미는 아니다. 기존 `expire_urgent()`의 종료된 방문 정보 24시간 후 정리 및 활동지역 변경 이력 1년 후 정리를 유지한다. 확정된 진행 중 약속은 시간이 지났다는 이유로 자동 만료시키지 않으므로, 미종료 약속의 보관 상한은 별도 확정이 필요하다. 정리 시 추가 약속 표와 제안 표의 장소도 함께 비운다. 원본 GPS·사진·녹음 제출 기능을 추가하지 않는다.

원복: `supabase/rollback_appointment_care.sql`. 미해결 제안·신고·이의제기·유효한 제한이 있으면 거부한다. 해소 후 저장한 함수 정의를 복원하고 새 UI 기능 응답을 비활성 상태로 바꾼다. 증거·회원·예약 표를 삭제하지 않는다. 프론트는 이번 작업 커밋을 되돌리며 원복 빌드/운영 적용도 별도 승인 대상이다.

## 알림과 운영 결정 필요 항목

- 앱 안 알림만 구현. 외부 메시지에는 연결하지 않았고 실제 사용자에게 아무것도 보내지 않았다.
- 요청·수락·장소 확인·확정·진행·지각·변경·취소·신고·판정에 맞는 일반 안내를 양쪽에 만든다. 주소·건강정보·신고 본문은 알림에 넣지 않는다.
- 예정 알림은 30분 전 구간에 생성하는 개발 기본값. `private.flush_appointment_reminders()`를 기존 작업 실행기에 연결할 준비가 되어 있다. **운영 예약 작업은 등록하지 않았다.** 화면을 연 상태에서는 같은 함수를 호출해 보완한다.
- 시행일·제한 안내 적용 시점, 유료 전문가 구독료/기간 처리와 사전 안내, 추가 사건의 수동 집행 절차, 이의제기 기한을 결정해야 한다.
- 사건 설명·판정·요청 해시·알림의 보관기간은 현행 문서에서 이 기능에 맞는 확정값을 찾지 못했다. 90일 계산에 필요한 기간과 이의제기 처리 기간을 포함하는 방안을 검토 대상으로 남긴다. 임의의 새 파기 기간/법적 문구를 확정하지 않았다.
- 실제 운영 스키마에 있는 별도 049·050 계열 기능과 이번 브랜치의 053·054 선행 적용 상태를 비교해야 한다. 운영 트리거와의 통합 검증은 아직 하지 않았다.
