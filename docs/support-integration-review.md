# 고객센터·관리자 통합 검증 — 2026-10-10

## 상태와 검증 범위

개발 브랜치 `codex/support-integration`에서 구현·격리 검증했다. **운영 Supabase 변경, 공개 배포, 실제 고객 알림, 실제 예약·결제 변경, 유료 AI 호출은 하지 않았다.**

현재 공개 고객센터는 `member_rights`와 `admin_member_rights`로 문의 한 건과 마지막 답변을 저장한다. `src/test-flow/support.js`의 자동안내는 별도 로컬 체험용 FAQ이며 운영 AI가 아니다. 이번 작업에도 AI 공급자나 외부 변경 도구를 연결하지 않았다. 화면 개선과 운영 가동 완료를 구분해야 한다.

검증은 기존 정적 HTML·esbuild·Supabase RPC 구조를 유지하고, PostgreSQL 호환 PGlite에 기존 SQL과 057 후보를 적용해 수행했다. 소비자·전문가·관리자 인증은 분리된 가상 세션이다. 브라우저의 모든 요청을 가로채 로컬 파일·격리 DB로 처리하며 나머지는 차단한다. 실제 Supabase 로그인, 원격 Postgres 병렬 부하, 실기기 키보드 검증을 대신하지 않는다.

| 작성 중 변경 | 고객의 새 메시지 뒤 오래된 화면에서 답변하면 차단. 초안을 유지한 채 최신 대화 확인 가능. 메모 저장이 답변 초안을 지우지 않음 |

| 모의 AI 장애 | 기존 대화 조회·추가 문의 가능, 운영자 확인 대상으로 남음. 자동 예약 변경 동작은 제공하지 않음 |
| 해결 확인 | 답변·침묵·경과시간만으로 해결 처리하지 않음. 고객 확인 기록이 있어야 해결로 집계. 재문의는 원래 대화를 다시 열음 |
| 권한 | 다른 고객·전문가의 대화 조회·추가 메시지 차단, 일반 회원의 관리자 주소·RPC 차단, 내부 테이블 직접 접근 차단 |
| 예약 연관 | 본인이 참여한 예약만 선택·연결. 관리자는 최소한의 예약 상태·일정 확인. 문의 작업 전후 예약 데이터 동일 |
| 부분 장애 | 전문가 심사 목록이 실패해도 관리자 문의함 이용 가능 |

| 호환·원복 | 기존 문의 RPC 호환, 057 반복 실행, 원복 후 기존 문의 조회 및 재적용 후 전체 대화 보존 |

실행 명령: `npm run test:support`. 관련 기존 회귀 검사는 `tests/early-access.test.mjs`와 `tests/support.test.mjs`도 수행했다. 상세 자동 결과는 `artifacts/support-integration-browser.json`, 화면은 `artifacts/support-customer-390.png`, `artifacts/support-operator-360.png`, `artifacts/support-operator-desktop.png`에 있다.

## ② 발견하고 수정한 오류

1. 접수 저장과 이력 갱신을 같은 실패 처리로 묶어, 실제 저장된 문의를 실패로 안내했다. 저장 결과와 조회 결과를 분리했다. 기존 DB용 화면에도 적용했다.
2. 추가 질문이 새 문의가 되고 운영자 답변은 덮어써지는 구조였다. 같은 문의에 메시지를 누적하고 원문을 보존한다.
3. 전송 결과가 유실되면 재전송 때 새 문의가 생성됐다. 사용자·전송 키 단위 영수증과 동일 내용 확인을 추가했다. 브라우저에는 본문 대신 전송 키·내용 지문·원래 변경 번호만 임시 저장한다. 운영자 답변도 저장 직후 응답이 끊긴 뒤 최신 대화를 조회하고 재전송해도 한 번만 남는다.
4. 관리자 최신순·최대 200건 구조에서 오래된 미답변이 밀렸다. 새 RPC는 미답변 대기 시점 우선과 페이지 이동을 제공한다.
5. 내부 메모와 공개 답변을 구분할 저장 구조가 없었다. 메시지 유형과 서버의 공개 응답 필드 목록으로 분리했다.
6. 오래된 관리자 화면이 최신 대화를 덮어쓸 수 있었다. 변경 번호 확인 및 초안 보존을 추가했다.
7. 고객센터가 전문가 심사 목록의 성공 여부에 묶여 있었다. 문의함을 먼저 별도로 표시한다.

수정 파일: `src/member-rights.js`, `src/early-operations-admin.js`, `src/early-expert-admin.js`, `src/support-ui.js`, `public/support.css`, 관련 HTML 2개, `package.json`, 신규 SQL·원복·검증 파일.

## DB 변경 후보와 원복

`supabase/057_support_conversations.sql`은 단일 트랜잭션·재실행 가능한 후보이다. **미적용 상태**다.

- 신규 비공개 테이블: `support_threads`(담당·대기·해결 상태), `support_messages`(원문·답변·메모), `support_receipts`(중복 실행 방지), `support_ai_runs`(모의 작업의 시작·완료 상태).
- 기존 문의·회원·예약 컬럼 삭제나 타입 변경 없음. 기존 저장 내용 삭제 없음. Storage 변경 없음.
- 새 테이블 RLS 활성화, 일반·인증 회원·서비스 역할의 직접 접근 회수. `support_command`는 로그인과 관리자·소유권 검사를 거쳐 동작한다.
- AI 시작·완료 함수는 비공개이며 브라우저·서비스 역할에 실행 권한을 주지 않았다. 새 문의는 AI 비활성 기본값이다. 실제 공급자·작업 실행기는 없다.
- 기존 문의 RPC를 사용하는 클라이언트도 문의가 새 대화 구조에 남도록 호환 트리거를 추가했다. 예전 운영자 답변 역시 진행 중인 모의 자동응답을 무효화한다.
- 원복: `supabase/057_support_conversations_rollback.sql`. 새 API와 자동응답을 중단하며 문의·대화·메모·이력을 삭제하지 않는다. 이전 화면을 복원하면 예전 방식으로 조회 가능하고, 새 대화 전체는 재적용 후 다시 표시된다.
- 원복 SQL에는 **새 함수 삭제**가 있으나 테이블·데이터 삭제는 없다. 새 대화 이력까지 예전 화면에 표시된다는 의미의 원복은 아니다.
- 운영 적용 시에는 별도 승인과 현재 운영 스키마 확인·백업·스테이징 검증이 필요하다. 이번 검증에서 운영 DB 백업이나 적용은 하지 않았다.

## ③ 미연동·미검증

- 실제 AI 답변·요약 생성, 내용의 정확성, 공급자 지연·중단·토큰 청구: 미연동. 통과한 것은 고정된 가상 답변의 저장·인수 경쟁 상태와 장애 처리다.
- AI가 예약·결제를 바꾸는 기능: 구현하지 않았다. 이미 외부에서 실행 중인 변경의 결과 정합성 검증도 해당 연결이 없으므로 완료로 보고하지 않는다.
- 외부 문자·이메일·푸시 알림: 발송하지 않았다. 고객은 같은 대화에서 새로고침 또는 재방문으로 답변을 확인한다.
- 실제 Supabase 로그인·운영 데이터·원격 Postgres 동시성: 미검증. 가상 세션의 DB 권한 및 작업 순서 경합 검증과 구분한다.
- 실제 휴대전화 키보드, 네트워크 복귀, 보조기기 사용: 실기기 확인 필요. 이번에는 Edge의 화면 폭·높이·글자 확대·키보드 조작을 확인했다.
- Claude Code 독립 검수: 아직 받지 않았다. 이 환경에서 실행 가능한 Claude Code 명령을 찾지 못했으며, 다른 작업에 검수를 전달하지 않았다. 아래 검수 범위로 읽기 전용 확인이 가능하다.
- 운영 반영 전이므로 현재 공개 사이트에서 새 대화 기능이 동작한다고 안내하면 안 된다. 057이 없는 DB에서는 기존 문의 화면을 유지한다. 그 기존 API의 통신 유실 재전송까지 서버에서 중복 방지된다는 뜻은 아니다.

## ④ 대표가 직접 해야 하는 남은 업무

- 운영 시작 시 미답변 문의를 열고 원문·예약 상태를 확인해 답변한다. AI 요약만으로 처리 여부를 결정하지 않는다.
- 검증용 환경에서 실제 로그인 계정으로 소비자·전문가·관리자 권한과 재접속을 최종 확인한다.
- Claude Code에 이 브랜치의 변경 파일을 읽기 전용으로 검수하도록 전달한다. 지적은 재현 후 반영하며 운영 DB 적용·배포는 이 검수에 포함하지 않는다.
- 실제 운영 DB 적용 및 화면 배포 여부는 검수 이후 별도로 결정한다.

## ⑤ 운영 시작 전 결정·최소 측정안

| 지표 | 기존 기록의 한계 | 이번 준비 상태 / 최소 후속 변경 |
| --- | --- | --- |
| 전체 문의 | 기존 문의 행 수로 확인 가능 | 문의 행 수 사용 |
| AI 응대 뒤 고객 확인 해결 | 기존에 AI·고객 확인 기록 없음 | 해결 확인 시 마지막 공개 답변 유형을 기록. 고객 확인이 있어야 AI 해결로 계산 |
| 운영자 검토 | 기존에는 모든 문의가 운영자 대상 | 현재 검토 대상 수 제공. AI 도입 시 전환 시점 이벤트를 별도로 남겨 기간별 전환 건수 집계 필요 |
| 재문의·미해결 | 답변이 있어도 해결인지 알 수 없음 | 같은 문의의 재열림 횟수, 고객 확인이 없는 문의 수. 미해결을 자동 완료로 바꾸지 않음 |
| 실제 처리시간 | 인수부터 답변까지 경과시간은 실제 작업시간이 아님 | 현재 미측정. 필요하면 운영자의 명시적 시작·중지 또는 화면 활성 구간을 기록하되 자리 비운 시간을 제외하는 방식 결정 |
| AI 사용량·비용 | 연결·과금 기록 없음 | 현재 미연동. 향후 공급자가 돌려준 사용량·비용과 요청 ID만 기록하고 값이 없으면 미확인으로 유지. 현재 0원으로 표시하지 않음 |

AI 도입 여부, 승인된 안내 원문과 답변 범위, 개인정보 외부 전송 범위, 비용 한도, 답변 시간 안내, 문의·내부 메모·전송 영수증의 보관 기준을 운영자가 결정해야 한다. 이 작업에서 새 환불 금액·답변 기한·보험 관련 판단을 만들지 않았다.

읽기 전용 검수 권장 순서: 057의 소유권·메모 필터 → 인수/완료 잠금 순서·변경 번호 → 전송 키의 재사용 → UI의 실패/초안 보존 → 기존 권리 요청과 원복. 가상 문의만 사용하며 운영 환경에 실행하지 않는다.
